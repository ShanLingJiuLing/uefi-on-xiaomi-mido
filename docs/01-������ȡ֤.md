# mido（Redmi Note 4X）移植 UEFI —— 可行性确认报告

> 实测日期：2026-11-02
> 设备：Xiaomi Redmi Note 4X 骁龙版（`mido`），序列号 `2ab8d34b9904`
> 方式：**纯只读采集**（adb + root shell + 拉取 DTB/分区头），未刷写、未改机
> 采集脚本与原始输出：`dumps/`（见文末清单）

---

## 0. 结论

**可行。而且比原调研档案估的更乐观。**

| 目标 | 判定 | 依据（本次实测） |
|---|---|---|
| ① EDK2 UEFI 在 mido 上点亮 | ✅ **可行** | lk2nd 已装机且在跑；屏幕已由 lk2nd 点亮并留下 20MB 连续 splash 缓冲；上游 lk2nd **已原生支持 mido** |
| ② UEFI 引导 ARM64 Linux | ✅ **可行** | 内核 `CONFIG_EFI_STUB=y`；eMMC 接口/分区结构已查清 |
| ③ Windows 10 ARM64 到桌面 | ⚠️ **条件可行** | `crc32` 指令**已确认存在**（硬门槛通过）；但 3GB RAM 偏紧、GPU/触摸/USB 全无驱动、ACPI 从零写 |
| Windows 11 ARM64 | ❌ **不可行** | Cortex-A53 r0p4 = ARMv8.0，无 LSE；Win11 24H2 起明确要求 ARMv8.1 |

三条最关键的实测事实：

1. **CPU 有 `crc32`**：`Features : fp asimd evtstrm aes pmull sha1 sha2 crc32` —— 原档案里"第一步就要查、查不到就直接放弃 Windows"的那一项，**通过了**。
2. **lk2nd 已经在 boot 分区里，并且就是当前引导器**：`/proc/cmdline` 结尾带 `lk2nd` 标记；boot 分区头 0x0 处是 327KB 的 lk2nd 镜像。也就是说"能 `fastboot boot` 任意 arm64 镜像"这条路**本来就是通的**，不需要先解锁、不需要先刷任何东西。
3. **屏幕不用自己写驱动**：面板是 `nt35532` FHD video mode，`mdss` 启动时打印 `bootloader display is on`，连续 splash 缓冲固定在 **0x90001000**（20MB）。EDK2 只需往这块内存画。

### 1.3 内存 —— 与原档案**不一致**，必须更正

`/proc/device-tree/memory` 与 `/proc/iomem` 实测：

```
memory 节点： reg = <0x0 0x40000000 0x0 0x40000000   0x0 0x80000000 0x0 0x80000000>
             → bank0: 0x40000000 + 1GiB
             → bank1: 0x80000000 + 2GiB
             → 合计 3GiB，最高地址 0xFFFFFFFF

**关键更正**：原档案（抄自 vince）写的 `0x10000000` 起址 **是错的**。mido 的 DRAM 起址是 **0x40000000**。

```

0x86800000 - 0x86BFFFFF   System RAM（4 MiB）
0x8EE00000 - 0xFFFFFFFF   System RAM（1.77 GiB）
（中间的空洞 = TZ / modem / adsp / wcnss / splash / pstore 保留区）
```

### 1.5 引导链现状 —— 这是最关键的发现

**boot 分区内容（直接读分区头验证）**：

```
0x00000000 : "ANDROID!"  kernel_size=335,320  kernel_addr=0x80008000  page=2048  → lk2nd（327 KB）
0x00080000 : "ANDROID!"  kernel_size=12,420,344  ramdisk=1,102,665  → 真正的 Android boot.img
```

即 **lk2nd 在 0x0，原 Android boot.img 被挪到 0x00080000（512 KiB）**。
（原档案写"1MB offset 机制"，实测是 **512 KiB**，细节更正。）

旁证：`/proc/cmdline` 与 `chosen/bootargs` 末尾都带 `lk2nd` 标记：

```
quiet core_ctl_disable_cpumask=0-7 kpti=0 noirqdebug androidboot.hardware=qcom
msm_rtb.filter=0x237 ... earlycon=msm_hsl_uart,0x78af000 ... buildvariant=userdebug
lk2nd androidboot.emmc=true androidboot.verifiedbootstate=orange ...
mdss_mdp.panel=1:dsi:0:qcom,mdss_dsi_nt35532_fhd_video:1:none:cfg:single_dsi
```

进入 fastboot 的两种方式（来自 mido 的 postmarketOS/Nura wiki）：

- **lk2nd fastboot**：正常开机，**震动后**按住音量下 ← 这才是我们要用的
- 原厂 fastboot：Power + 音量下（会走 aboot，屏幕不会由 lk2nd 初始化）

### 1.6 显示

```
cmdline 指定面板： qcom,mdss_dsi_nt35532_fhd_video（BOE / Novatek NT35532，FHD，video mode，single DSI）
dmesg：mdss_mdp_probe: mdss version = 0x10100000, bootloader display is on, num 1, intf_sel=0x00000100
       dsi_panel_device_register: Continuous splash enabled
       mdss_register_panel: adding framebuffer device 1a94000.qcom,mdss_dsi_ctrl0

Android 侧 fb0： name=mdssfb_80000  1080x3840(virtual, 3 屏)  stride=4352  bpp=32
splash 缓冲   ： 0x90001000，size 0x13FF000（20 MiB，够 2.5 屏 32bpp）
```

要点：
- **没有 `/sys/class/drm`** —— 该内核走 **fbdev（mdssfb）**，不是 DRM。这不影响 UEFI，因为我们只用 splash 缓冲。
- stride 4352 = 1088×4，即 **32bpp、按 1088 对齐**（不是档案里从 mainline DTS 抄的 RGB888/3240）。
- **GOP 可以直接建在 0x90001000 上**：1080×1920×32bpp、stride 4352 只占 8.36 MB，20 MB 区域足够。

**更正 1**：触摸不是"`edt,edt-ft5406` 芯片"——实际是 **focaltech FT5435**。但**地址 0x38、总线 i2c-3、IRQ gpio65、reset gpio64 全部与档案一致**；mainline/lk2nd 正是用 `edt,edt-ft5406` 这个 compatible 去绑 focaltech，所以档案的结论没错，只是名字来源不同。上游 lk2nd 的 mido 五个面板条目**全部**写 `touchscreen-compatible = "edt,edt-ft5406"`，可以互证。

## 3. 可行性逐阶段判断（含工作量重估）

```
PBL(ROM) → XBL → aboot(LK, 已解锁) → [boot 分区] lk2nd(0x0, 327KB)
                                        ├─ 正常开机 → 0x80000 的 Android boot.img
                                        └─ fastboot boot <img> → 直接加载并跳转  ← 我们要用的
                                             ↓
                                        EDK2 UEFI（内核加载地址 0x80008000，与 lk2nd 自身一致）
                                             ├─ GOP ← 复用 0x90001000（面板已由 lk2nd 点亮）
                                             ├─ UARTDM SerialPortLib ← 0x078AF000 / SPI 107
                                             ├─ SDHCI eMMC ← 0x07824900
                                             └─ 喂狗 ← 0x0B017000，bark=11s
```

| 阶段 | 判定 | 现在的难度 | 相对原估 |
|---|---|---|---|
| 0 环境/取证 | ✅ **已完成** | — | 本次做完 |
| 1 EDK2 骨架 + 点亮 | ✅ 可行 | **降为"中等"**：显示、面板、引导链全有现成答案 | 说明从 1–2 月压到 **2–4 周** |
| 2 eMMC + Linux EFI stub | ✅ 可行 | 中：需自建 SDCC1 时钟/复位序列（不能靠 aboot） | 不变，+2–4 周 |
| 3 ACPI | ⚠️ 硬骨头 | 高：DSDT/SSDT 全手写（GIC/GTDT/SBSA-UART/SDHCI/XHCI/I2C/GPIO/电池/热区） | 不变，数月 |
| 4 Win10 ARM64 桌面 | ⚠️ 条件可行 | **很高**：能进系统 ≠ 能用 | 不变 |

### 为什么"点亮"比原估计容易

1. **面板不用管**：lk2nd 的 `target/msm8953/oem_panel.c` + `target_display.c` 已包含 mido 的全部 5 种面板时序，且 mido 有 `lk2nd,match-panel`（自动读面板 ID）。EDK2 只写显存。
2. **引导链不用造**：`fastboot boot` 已是成熟通路，且 **lk2nd 震后按音量下就能进 fastboot** —— 即使 Android 被搞坏，也有一条固定入口，不必担心变砖（见 §5）。
3. **不需要 DT→ACPI 转换**：mido 目前跑 mainline 也只靠 DT，我们用 DTB 只做"事实字典"。

### 为什么 Windows 这条仍是"能跑但不好用"

- **GPU**：Adreno 506 无 Windows 驱动 → 只能 Microsoft Basic Display（软件渲染，1080p 会很卡）。
- **触摸**：focaltech 无 Windows 驱动 → 只能 USB 鼠标。
- **WiFi/BT**：WCNSS 是 QMI 子系统，Windows 无驱动。
- **3GB RAM**：Win10 ARM64 勉强够（最低 2GB），但加上 24GB 可用存储，属于"能看见桌面"的量级。
- **ACPI 从零写**：这是整个项目最大的一块工作量，也是决定"能不能进安装器"的分水岭。

## 4. 新的风险登记册（按优先级，全部实测更新）

| 优先级 | 风险 | 实测依据 | 对策 |
|---|---|---|---|
| **P0** | **AP watchdog 11 秒咬人** | `qcom,wdt@b017000`：`bark-time=0x2AF8(11s)`、`pet-time=0x2490(9.36s)`、`ipi-ping` | EDK2 一启动就挂一个周期事件写 `WDT_RST`，或在 BootShim 里先关狗。**不处理的话，所有"莫名其妙重启"都是这个**，别误判成代码 bug |
| **P0** | 主机没有 `fastboot.exe`，也没看到 Android bootloader 驱动 | `Get-Command fastboot` 空；`pnputil` 无 android/winusb 条目；设备当前是 `VID_18D1&PID_4EE2` | 装 platform-tools + Google USB Driver（或等 Windows Update 的 Android Bootloader Interface）。**这是开工前第一件要解决的事** |
| P1 | 无 UART 引出（未证实） | 档案说"Linux 无 console"，但 SoC 侧 UART 确定在 0x078AF000 且 earlycon 已配 | 需开壳找测试点；退路：屏幕色块检查点 + `pstore@0x9FF00000` + lk2nd fastboot 可回滚 |
| P1 | `fastboot boot` 只接受 Android boot.img 格式 | boot 分区两块镜像都是 `ANDROID!` 头，kernel_addr 均 0x80008000 | EDK2 产物要按 boot.img 封装（kernel=UEFI FD+BootShim），不能塞裸 FD |
| P1 | eMMC 时钟/复位需自建 | 内核由 `qcom,sdhci-msm` 驱动负责，EDK2 里没有 | 从 lk2nd `target/msm8953` 的 SDCC 初始化代码移植 |
| P2 | 3GB/4GB memory map 不同 | 本机 3GB（已取真值） | 从 lk2nd 传的 DTB / SMEM 动态读，**不写死** |
| P2 | 保留区踩踏 → 随机死机 | 0x84A00000/0x86C00000/0x8D600000/0x8E700000/0x90001000/0x9FF00000 六块 | 用本报告 §1.3 的表逐块跳过 |
| P2 | dwc3 默认 peripheral | `ssusb mode: peripheral`，`dr_mode` 同 | UEFI 里重新按 host 初始化 + 切 `ssusb_mode_sel`(gpio12) |
| P3 | 无充放电管理 | PM8953/PMI8950，电池 70% 健康 | 短时测试可接受；ACPI 里再描述 |
| P3 | 变砖 | `aboot` 完好、EDL 未测 | 只要坚持 `fastboot boot`（不 flash），风险≈0；先验证 9008 通道更稳妥 |
| P3 | 设备时钟偏差 ~11 个月 | 文件时间戳 2025-12-22 vs 系统时间 2026-11-02 | 拉取 UUP 镜像时用主机时间即可，无实际影响 |

## 5. 现在这台机器的"安全边界"（为什么可以先放心试）

- **不 flash 就不可能变砖**：`fastboot boot` 只把镜像读进 RAM 再跳转，boot 分区一个字节都不动。任何失败 → 长按电源关机 → 正常开机回 LineageOS。
- **lk2nd fastboot 走的是"震动后按音量下"**，不依赖 Android 好坏（Android 崩了也进得去）。
- **aboot（1 MiB）完好**，`sbl1/tz/rpm` 等都在；必要时还能回原厂刷机包。
- boot 分区里 **lk2nd 与原 Android boot.img 共存**（0x0 / 0x80000），说明这套"双镜像"机制本来就在工作。

## 6. 建议的下一步（仍不动手，只需你确认三件事）

1. **主机齐备**：装 platform-tools（要有 `fastboot.exe`）+ Android bootloader WinUSB 驱动，然后进一次 lk2nd fastboot 跑 `fastboot getvar all`，确认能认到设备（这一步不刷任何东西）。

### 7.1 关键发现：lk2nd 把 boot 分区虚拟拆成了两个

| 名字 | 类型 | 大小 | 实际位置 |
|---|---|---|---|
| `lk2nd` | raw | `0x80000`（512 KiB） | boot[0x00000, 0x080000) |
| `boot` | raw | `0x3f80000`（63.5 MiB） | boot[0x080000, 0x4000000) |

GPT 里只有**一个** 64 MiB 的 `boot`（Android 侧 `by-name` 也是这么列的），所以这是 **lk2nd 自己做的虚拟切分**——与 §1.5 用 dd 读到的 0x0 / 0x80000 两个 `ANDROID!` 头**完全对上**。

> **这让部署安全性直接拉满**：
> - `fastboot boot <img>`：只进 RAM，一个字节都不写；失败 = 重启
> - 即使真去 `fastboot flash boot edk2.img`，写的也是 0x80000 之后，**lk2nd 那 512 KiB 不受影响**，随时可回滚
> - 原厂 `aboot`（1 MiB）还在，是最后一道底线

### 8.4 附带踩到的环境坑（已解决，备忘）

platform-tools 37 的 `adb.exe` 在本机直接跑会连续报两个错：

```

## 9. 封装通道闭环验证：自建 boot.img + DTB 注入（2026-11-02）

这一步把 §8 剩下的唯一未知项（"lk2nd 到底要什么样的镜像"）从源码和实测两头钉死了。

### 9.1 lk2nd 的 DTB 判定逻辑（读源码，不是猜）

`app/aboot/aboot.c` → `boot_linux_from_memory()`：

1. `is_gzip_package(kernel, kernel_size)` 为真 → 调 `decompress()`，由它回填 `dtb_offset`
2. 否则（**裸载荷**）→ 调 `dev_tree_appended(kernel, kernel_size, 0, tags)`
3. `dev_tree_appended()`：`memcpy(&app_dtb_offset, kernel + DTB_OFFSET, 4)`，而

   ```c
   /* platform/msm_shared/include/dev_tree.h */
   #define DTB_OFFSET 0x2C
   ```

4. 从 `kernel + app_dtb_offset` 开始扫描 FDT；当 `dtb_count == 1` 且兼容队列为空时**强制选中**这一个 DTB
5. 两条路都失败 → 回退 `lk2nd_device2nd_have_atags()`（mido 上是 ATAGS 通路）→ 再失败才 `fastboot_fail("dtb not found")`
6. 全程**不校验内核是什么**：`memmove` 到 `hdr->kernel_addr` 之后直接 `boot_linux()` 跳转

> 这解释了 §8 的两次现象：垃圾镜像走裸载荷路径、`+0x2C` 里是 `0xAAAAAAAA`，扫描越界 → 失败；
> 真实 Android 镜像的内核是 **gzip**（`1f 8b 08`），走 `decompress()` 路径，DTB 在压缩流之后（kernel+0xB97828）被自动找到。

### 9.2 新工具：`tools/mkbootimg.py`

纯 Python 的 boot.img v0 打包/解析器，无外部依赖：

```powershell

python tools/mkbootimg.py selftest test/android-boot.img   # 逐字节复现自检
```

自检结果：**13,527,040 字节完全复现**，仅 id 字段（offset 576，SHA1）不同 —— 那是 LineageOS 用的改版组合，lk2nd 不校验，可忽略。

### 9.3 探针镜像 `test/probe.img`（268,288 B）—— 四件事一次证明

载荷布局：

```

0x08  0x0000000000000000 (u64)     ; 刻意置 0：lk2nd 的 text_offset hack 只在 >2MB 时才写
0x2C  u32 = 0x60                   ; ★ DTB_OFFSET → DTB 在载荷内的偏移

          adb devices      → 2ab8d34b9904  device

| # | 结论 |

### 10.6 两个必须自己解决的定制点

**① BootShim 要留 trampoline 头**

`dev_tree_appended()` 会读 `*(u32*)(kernel+0x2C)` 并**扫描 FDT**；同时 `boot_linux_from_memory` 会对 `*(u64*)(kernel+8)` 做 `text_offset` hack。
`tools/BootShim/BootShim.S` 开头就是代码，`+0x2C` 会落在指令上。所以 mido 版 BootShim 必须：

```
0x00  b +0x40        ; 跳过头部
0x08  0 (u64)        ; text_offset 保持 <=2MB，避免被 lk2nd 清零
0x2C  u32 = DTB 偏移 ; 由打包脚本回填
0x40  <BootShim 真正入口>
```

**② 打包不能用 `abootimg`**

`Silicon/Qualcomm/msm8998/platform.sh.inc` 的 `platform_build_bootimg()` 用 `abootimg`，它不支持"往 kernel 里塞 DTB 偏移"。
mido 的 `platform.sh.inc` 要改成调用我们自己的 `tools/mkbootimg.py`（已在 PC 侧验证过，见 §9），把 BootShim + DTB 一起打包。

### 10.7 mido 的首版 PCD 草案（基于实测地址）

```

### 11.0 先更正 §10.6 / §10.7 的两条判断

§10.6 是根据"裸载荷 + `+0x2C`"推出来的，实际读源码后发现**上游走的是 gzip 路径**，
所以两条都不再需要：

### 11.3 打包钩子（关键修正）

上游通用钩子用 `mkbootimg.py` 的默认 `--base 0x10000000`，算出来 `kernel_addr = 0x10000000`。
**mido 的 DRAM 从 0x40000000 起**，这个地址在 DRAM 之外，lk2nd 的 `check_ddr_addr_range_bound()`
会直接判 "kernel/ramdisk addresses are not valid"。

`Silicon/Qualcomm/msm8953/platform.sh.inc` 改成显式指定与本机原厂镜像一致的地址：

```
--base 0x80000000 --kernel_offset 0x00008000   -> kernel  0x80008000
--ramdisk_offset 0x01000000                    -> ramdisk 0x81000000
--tags_offset    0x00000100                    -> tags    0x80000100
```

### 11.5 首次运行前已知的待验证/待改项

| 项 | 现状 | 风险 |

## 12. 阶段 1 达成：UEFI 在 mido 上启动并进入 Shell（2026-11-04）

### 12.1 结果

```
lk2nd → BootShim → PrePi → DxeCore → BDS → Renegade logo / Boot Menu → UEFI Shell
```

**显示完全正常**，Boot Menu 与 Shell 文字清晰、无错位。至此原档案的"目标① EDK2 UEFI 在 mido 上点亮"完成。

### 12.2 一路踩过的 5 个坑（按出现顺序，每个性质都不同）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 只有固件横幅，随后整机死掉且不重启 | `PlatformUtils.h` 的 `APSS_WDT_BASE` 是从 msm8998 抄的 `0x17817000`，在 msm8953 上**未映射**；`SetWatchdogState()` 一写就外部中止，而 EL2 尚无异常向量 | 改为 **`0x0B017000`** |
| 2 | 改完仍然只有横幅 | EDK2 增量构建**没有重编**该模块，`boot-mido.img` 与上一版 md5 完全相同（差点在同一个镜像上白测一次） | `touch` 全部源码 + 删除该 SoC 构建产出后重编 |
| 3 | 数据中止 @ `ArmGicDxe+0x2C18`，FAR 反推地址 `0xB` | `PcdGicInterruptInterfaceBase` 是 `[Pcd.common]` 动态 PCD，**默认值 0**，我们漏设；`ArmGicV2Dxe` 把它直接喂给 `MmioWrite32(base + ARM_GIC_ICCBPR, 7)` | DSC 补 **`PcdGicInterruptInterfaceBase\|0x0B002000`** |
| 4 | 数据中止 @ `SmemDxe`，`FAR = 0x01FD4000` | 借用的**msm8998 预编译二进制**访问 msm8998 专属地址（DloadCookie `0x01FD3000` 一带），符号路径直接暴露 `/…/MSM8998_WP10/…` | 从 `msm8953.fdf` 移除 `Apriori.fdf.inc` 与 `dxe.fdf.inc` 两个 include，**整套预编译驱动剔除** |
| 5 | Shell 画面文字重叠/错位（早期 M0–M17 日志却正常） | `SimpleFbDxe.c` 写死 `FB_BITS_PER_PIXEL 32`，而面板是 **24bpp RGB888**；32bpp 写进 24bpp 缓冲 → 每行偏 1080 字节 | GOP 用 **32bpp 影子缓冲**，`DisplayBlt` 后把目标矩形转 24bpp(B,G,R) 写真实面板缓冲 |

### 12.3 被实测修正的三个参数（都很反直觉）

| 参数 | 最初判断 | 实测正确值 | 怎么发现的 |
|---|---|---|---|
| 帧缓冲像素格式 | 32bpp / stride 4352（来自 Android `fb0`） | **24bpp / stride 3240** | 按 32bpp 填充时出现**每 3 列一组的竖条纹**——24bpp 下 4 字节写入的相位假象 |
| GIC CPU 接口基址 | 以为 Distributor 对就够 | 还必须显式设 **`0x0B002000`** | 反汇编 `ArmGicDxe.dll`，定位到 `MmioWrite32(0x3+8, 7)` |
| msm8998 预编译驱动 | 以为"改几个地址"就能用 | **完全不可用** | `SmemDxe` 崩溃时 FAR 落在 msm8998 的 DloadCookie 地址 |

### 12.4 方法上的两条经验（可直接复用）

1. **反汇编定位法**：异常处理器会打印 `PC (基址+偏移)`。在设备上
   `aarch64-linux-gnu-objdump -d <驱动>.dll` 找该偏移，就能看到**具体哪条指令、操作了哪个地址**，
   比读源码猜快一个数量级（坑 3 靠 `X2=0xB` 反推）。
2. **心跳 + 阶段标记**：`BootShim.S` 刷两块不同灰度、`PrePi.c` 插 `[mido] M0..M18`
   （用 `EFI_D_ERROR`，RELEASE 也打印）。无 UART 的机器上，这是把"卡在哪一步"变成可观测量的唯一手段。
