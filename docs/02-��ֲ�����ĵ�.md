## 1. 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│  硬件 PBL (ROM)                                              │
│    ↓ 校验并加载                                              │
│  XBL / sbl1                                                  │
│    ↓                                                         │
│  aboot / LK（原厂引导器，bootloader 分区，已解锁）            │
│    ↓ 读 boot 分区 0x00000                                    │
│  lk2nd  ── 二级引导器，被当成"内核"加载                       │
│    ├─ 初始化 DSI 面板 / MDP，点亮屏幕（留 20MB cont-splash）  │
│    ├─ 面板自动识别（mido 支持 5 种面板）                       │
│    ├─ 提供 fastboot（震动后按音量下进入）                      │
│    └─ 若没人干预，链式启动 boot 分区 0x80000 的原 Android 镜像 │
│    ↓ fastboot boot <img>                                     │
│  BootShim（144→208 字节的 AArch64 跳板）                      │
│    ↓ 把 FD 拷到 FD_BASE 并跳转                                │
│  EDK2 PrePi (SEC)                                            │
│    ↓ 建 HOB / 页表 / 解压内层 FV / 载入 DxeCore               │
│  DxeCore → 驱动分发 → BDS → Boot Menu → UEFI Shell           │
└─────────────────────────────────────────────────────────────┘
```

**关键设计选择**：不从零写引导器，而是把 EDK2 塞进 lk2nd 的 "kernel" 槽位。
好处是面板初始化、fastboot 通道、救援入口全部由成熟的上游代码提供。

### 1.1 为什么这条路可行

| 条件 | 为什么成立 |
|---|---|
| lk2nd 已在 boot 分区 | 原机主早已刷过；`/proc/cmdline` 尾部带 `lk2nd` 标记可确认 |
| lk2nd 不校验内核类型 | 源码里 `boot_linux_from_memory()` 只做 `memmove` + `boot_linux()`，跳转前不看载荷内容 |
| 屏幕不用自己点 | lk2nd 已经配好 DSI/MDP，EDK2 只需往固定物理地址画 |
| 上游 lk2nd 支持 mido | `lk2nd/device/dts/msm8953/msm8953-xiaomi-common.dts` 里有 `mido { }` 节点 |

## 2. 启动链原理

### 2.1 boot 分区的真实布局

用 `dd` 直接读分区头确认（`lk2nd` 把 GPT 里的一个 `boot` 分区**虚拟拆成两个**）：

| fastboot 名字 | 大小 | 实际位置 | 内容 |
|---|---|---|---|
| `lk2nd` | `0x80000`（512 KiB） | boot[0x00000, 0x80000) | lk2nd 自身（`ANDROID!` 头 + 327 KB 载荷） |
| `boot` | `0x3f80000`（63.5 MiB） | boot[0x080000, 0x4000000) | 原 Android boot.img（内核 12.4 MB + ramdisk 1.1 MB） |

这意味着：**即使真的 `fastboot flash boot edk2.img`，lk2nd 那 512 KiB 也不受影响**，随时可回滚。

### 2.2 lk2nd 装载一个镜像时做了什么

对应 `app/aboot/aboot.c` 的 `boot_linux_from_memory()`：

```
1. 解析 boot_img_hdr（page_size / kernel_size / addr / ramdisk / tags）
2. is_gzip_package(kernel) ?
   是 → decompress()，由解压器回填 dtb_offset
   否 → 裸载荷路径，dtb_offset 取自 *(u32*)(kernel + 0x2C)
3. copy_dtb() 失败（镜像里没有 dt 段）后：
   dev_tree_appended(kernel, kernel_size, dtb_offset, tags)
       → 从 kernel + dtb_offset 起扫描 FDT
       → 找到 1 个且兼容队列为空时，强制选中
4. 两条路都失败 → 回退 lk2nd_device2nd_have_atags() → 再失败才 fastboot_fail("dtb not found")
5. check_ddr_addr_range_bound(kernel_addr, kernel_size) —— mido 的 DRAM 从 0x40000000 起
6. memmove(ramdisk) / memmove(kernel → kernel_addr)
7. fastboot_okay("") → boot_linux(kernel_addr, tags, cmdline, ...) —— 直接跳转
```

**第 7 步是全部可行性的来源**：跳转前不检查载荷是不是 Linux 内核。

### 2.3 BootShim 的作用

`tools/BootShim/BootShim.S` 是一个位置无关的 AArch64 小段：

```asm
_Head:
    adr  x1, _Payload      ; x1 = 紧跟其后的 FD 起始
    b    _Start
    ...                    ; 伪造的 Linux Image 头（0x08=text_offset=0，
                           ;  0x38="ARM\x64"，0x40="EDK2-MSM"）
_Start:
    mov  x4, x1
    ldr  x5, _StackBase    ; = UEFI_BASE (FD_BASE)
    ldr  x6, _StackSize    ; = UEFI_SIZE (FD_SIZE)
_CopyLoop:
    ldp  x2, x3, [x4], #16 ; 把 FD 拷到 FD_BASE
    stp  x2, x3, [x5], #16
    subs x6, x6, #16
    b.ne _CopyLoop
    br   x5                ; 跳到 FD 入口
```

要点：
- **位置无关**（全部 PC 相对），所以 `kernel_addr` 只要落在合法 RAM 即可
- 它把 FD 拷贝到 `FD_BASE`，因此 **FD 的链接地址必须等于 FD_BASE**
- 0x2C 落在伪造头的保留字段里，正好可以用来放 DTB 偏移（本项目没用上，但留了余地）

## 3. 镜像封装原理

### 3.1 最终产物结构

```
boot-mido.img  (Android boot image, header v0, page 2048)
├── header (2048 B)     kernel_addr=0x80008000  ramdisk_addr=0x81000000  tags=0x80000100
└── kernel (gzip 压缩)
     ├── 解压后 = BootShim.bin (208 B) + MSM8953_UEFI.fd (0x700000 B)
     └── 压缩流之后追加 mido.dtb (266,044 B)
```

### 3.2 三个必须对齐的数字

| 项 | 值 | 为什么 |
|---|---|---|
| `kernel_addr` | `0x80008000` | mido 的 DRAM 从 **0x40000000** 起；上游 `mkbootimg.py` 默认 `base=0x10000000` 会算出 DRAM 外的地址，被 lk2nd 的地址检查直接拒绝 |
| `ramdisk_addr` | `0x81000000` | 与原厂镜像一致，且不与 7 MB 内核重叠 |
| `tags_addr` | `0x80000100` | lk2nd 会把选中的 DTB 拷到这里 |

对应 `Silicon/Qualcomm/msm8953/platform.sh.inc`：

```bash
python3 "${ROOTDIR}/tools/mkbootimg.py" \
    --kernel  "${WORKSPACE}/uefi-${DEVICE}-kernel" \
    --ramdisk ramdisk \
    --base 0x80000000 --kernel_offset 0x00008000 \
    --ramdisk_offset 0x01000000 --tags_offset 0x00000100 \
    -o "${OUTDIR}/boot-${DEVICE}.img"
```

### 3.3 为什么要 gzip

不只是为了体积。上游 `Silicon/platform.sh.inc` 的 `platform_build_kernel()` 做三件事：

```bash
cat BootShim.bin MSM8953_UEFI.fd > uefi-mido.fd-bootshim
gzip -c < uefi-mido.fd-bootshim > uefi-mido.img.gz
cat uefi-mido.img.gz FdtBlob_compat/mido.dtb > uefi-mido-kernel
```

即 **"压缩 → 在压缩流尾部追加 DTB"**。而这个布局正好命中 lk2nd `decompress()` 的分支，
由解压器回填 `dtb_offset`，从而绕过"裸载荷必须自己维护 `+0x2C`"的麻烦。

### 3.4 DTB 从哪来

`Platform/Xiaomi/msm8953/FdtBlob_compat/mido.dtb` = 从真机 `/sys/firmware/fdt` 导出的
266,044 字节 DTB（`qcom,msm-id=293`、`qcom,board-id=11`）。它的唯一作用是让 lk2nd 的
`dev_tree_appended()` 满意——EDK2 自己并不消费它。

## 5. 内存图与页表

### 5.1 为什么这个文件最关键

`PlatformMemoryMapLib` 返回的描述符数组是 **PrePi 建页表的唯一依据**。
凡是没有被描述的地址，一旦被访问就是 `Translation fault, second level` —— 这正是
坑 3（GIC 基址=3 → 写地址 0xB）崩溃的机制。

### 5.2 mido 的实际映射

```
0x00000000 – 0x3FFFFFFF  MMIO    外设窗口（TLMM/GCC/MDSS/GIC/SPMI/UART/SDCC/USB/IMEM/SMEM）
0x40000000 – 0x849FFFFF  Conv    可用
0x84A00000 – 0x867FFFFF  Reserv  TZ / other_ext（30 MiB）
0x86800000 – 0x86BFFFFF  Conv    可用（4 MiB）
0x86C00000 – 0x8D5FFFFF  Reserv  modem 固件（106 MiB）
0x8D600000 – 0x8E6FFFFF  Reserv  adsp 固件（17 MiB）
0x8E700000 – 0x8EDFFFFF  Reserv  wcnss 固件（7 MiB）
0x8EE00000 – 0x8F4FFFFF  BsData  UEFI FD（FD_BASE）
0x8F500000 – 0x8FFFFFFF  Conv    可用
0x90000000 – 0x90000FFF  Reserv  dfps
0x90001000 – 0x913FFFFF  Reserv  ★ lk2nd 连续 splash = GOP 帧缓冲（写通）
0x91400000 – 0x91400FFF  BsData  CPU 向量
0x91401000 – 0x91403FFF  BsData  MMU 页表
0x91404000 – 0x91443FFF  BsData  UEFI 栈
0x91444000 – 0x9F1FFFFF  Conv    可用
0x9F200000 – 0x9F2FFFFF  BsData  SimpleInit DT 存放区
0x9F300000 – 0x9FEFFFFF  Conv    可用
0x9FF00000 – 0x9FFFFFFF  Reserv  pstore / ramoops
0xA0000000 – 0xFFFFFFFF  Conv    DXE 堆（1.5 GiB）
```

**必须避开**的六块（写进去会踩坏其他子系统或崩溃）：
`0x84A00000`、`0x86C00000`、`0x8D600000`、`0x8E700000`、`0x90001000`（帧缓冲除外的部分）、`0x9FF00000`。

### 5.3 一个容易忽略的细节

RAM 分区与 BsData 分区必须**首尾相接地覆盖整个可用区间**，不能有缝：
例如 `0x91444000 + 0x0DBBC000 = 0x9F200000`，否则中间那块既不是内存也不是 MMIO，
DxeCore 分配时可能撞上未映射区。

## 6. 显示路径与 SimpleFbDxe

### 6.1 两条显示通路

| 通路 | 用途 | 实现 | 像素格式 |
|---|---|---|---|
| `FrameBufferSerialPortLib` | PrePi/DXE 的 DEBUG 文字（**无 UART 时的救命通道**） | 直接按 5×12 字模写 `PcdMipiFrameBufferAddress` | 按 `PcdMipiFrameBufferPixelBpp`，本项目设 **24** |
| `SimpleFbDxe` → GOP | 图形控制台 / 菜单 / Shell | 建 GOP，`GraphicsConsoleDxe` 在上层合成 | **上游写死 32bpp**，本项目改造 |

### 6.2 关键结论：面板是 24bpp，不是 32bpp

从 Android `/sys/class/graphics/fb0` 读到的是 `32bpp / stride 4352`，那是 **Android 内核重新配置 MDP 之后**的状态。
lk2nd 留下的缓冲是 **24bpp RGB888、stride 3240（= 1080×3）**。

判定依据（非常直观）：按 32bpp 每像素写 4 字节时，屏幕上出现**每 3 列一组的彩色竖条纹**——
这是 4 字节写入落进 3 字节像素栅格时的相位假象。

### 6.3 24bpp 适配做法

GOP 标准里**没有 24bpp 的像素格式**（只有 RGBx/BGRx/BitMask/BltOnly），所以：

```c
if (PcdMipiFrameBufferPixelBpp == 32) {
    /* 原生路径，与上游一致 */
} else {
    /* 分配 32bpp 影子缓冲 (1080*1920*4 = 8.3 MB)，GOP 只认它 */
    Shadow = AllocatePool(FrameBufferSize);
    ZeroMem(Shadow, FrameBufferSize);
    mDisplay.Mode->FrameBufferBase = (EFI_PHYSICAL_ADDRESS)(UINTN)Shadow;
    mNeedsConversion = TRUE;
}
```

每次 `DisplayBlt()`：

```
FrameBufferBlt(影子缓冲, 请求的矩形)      ← 上游逻辑原样保留
ConvertRectTo24bpp(DestinationX/Y, W, H)  ← 把该矩形转 B,G,R 写进 0x90001000
WriteBackInvalidateDataCacheRange(...)
```

转换只处理**被触碰的矩形**，所以菜单局部重绘不会整屏重算。

> 副作用：`SimpleFbDxe.inf` 的 `[FixedPcd]` 必须补上 `PcdMipiFrameBufferPixelBpp`，
> 否则 `PcdLib.h` 会报 `_PCD_VALUE_PcdMipiFrameBufferPixelBpp undeclared`。

## 7. 按键驱动

### 7.1 硬件事实

| 键 | 接到哪 | EDK2 可达？ |
|---|---|---|
| 音量 **上** | TLMM **GPIO 85**，低有效 + 上拉 | ✅ |
| 音量 **下** | PMIC **PON2**（`qcom,pon_2`, `linux,code=0x72`） | ❌ 需要 SPMI |
| 电源 | PMIC PON1 | ❌ 同上 |

依据：Live DTB `/soc/gpio_keys/vol_up` → `gpios = <&tlmm 0x55 0x1>`，`linux,code = 0x73`。

### 7.2 TLMM 寄存器布局

来自 lk2nd `platform/msm8953/include/platform/iomap.h`（这份代码在真机上跑过，可信）：

```c
#define TLMM_BASE_ADDR      0x01000000
#define GPIO_CONFIG_ADDR(n) (TLMM_BASE_ADDR + (n) * 0x1000)              // 配置
#define GPIO_IN_OUT_ADDR(n) (TLMM_BASE_ADDR + 0x4 + (n) * 0x1000)        // bit0 = 输入电平
```

配置成"GPIO 功能 + 上拉 + 输入"：

```c
Cfg  = MmioRead32 (GPIO_CFG_ADDR (pin));
Cfg &= ~((0x3 << 2) | (0x3 << 0) | (1 << 9));   // 清 func / pull / OE
Cfg |= (0 << 2) | (3 << 0);                     // func=GPIO, pull-up
MmioWrite32 (GPIO_CFG_ADDR (pin), Cfg);
```

### 7.3 交互设计：一个键干完所有事

因为只有音量上可用：

| 手势 | 产生的键 |
|---|---|
| 短按（< 800 ms） | `SCAN_DOWN`（向下移动选择） |
| 长按（≥ 800 ms） | `Enter`（确认） |

按下时记 `GetPerformanceCounter()`，松开时算时长并与 800 ms 比较。

### 7.4 为什么最后没用定时器

第一版用 `gBS->CreateEvent(EVT_TIMER)` + `SetTimer(10 ms)` 采样。
结果：按键无反应，且"3 秒后自动重启"的探针也不触发 → **定时器回调根本没跑**
（或该固件下 `gRT->ResetSystem` 不可用）。

最终方案：**把采样塞进 ConIn 的调用路径里**，完全不依赖定时器。

```c
ButtonsReadKeyStroke()  → SampleKeys() → 有键则返回
WaitForKeyNotify()      → SampleKeys() → 队列非空则 SignalEvent
ButtonsReset()          → SampleKeys() → 清空
```

因为 BDS/菜单本来就在不停地 `ReadKeyStroke` 或等 `WaitForKey`，这等价于一个
"由消费者驱动"的轮询，且不会漏掉"按下-松开"的完整边沿。

### 7.5 与 ConSplitter 的衔接

驱动只做两件事：`InstallMultipleProtocolInterfaces(&Handle, &gEfiSimpleTextInProtocolGuid, ...)`。
`ConSplitterDxe` 通过协议通知自动接管，把我们的按键并入 `ConIn`，BDS 无需任何改动。

## 8. 调试方法论

没有 UART 的机器上，"看不见"是最大的敌人。本项目逐步攒出一套可复用的手段。

### 8.1 三层可观测性

| 层 | 手段 | 能回答什么问题 |
|---|---|---|
| BootShim | 往帧缓冲刷**不同灰度**（`0x80808080` 三字节相同，24/32bpp 下都是纯灰） | 载荷到底有没有执行？FD 拷完了吗？ |
| PrePi | `[mido] M0..M18` 标记，用 `EFI_D_ERROR` 级别（RELEASE 也打印） | 卡在哪个子系统初始化？ |
| DXE | 异常处理器自带符号化调用栈 + 寄存器快照 | 崩在哪个驱动、哪条指令、访问哪个地址？ |

### 8.2 反汇编定位法（本项目最有效的一招）

异常输出形如：

```
PC 0x0000FC305C18 (0x0000FC303000+0x00002C18) [0] SmemDxe.dll
ESR: EC 0x25 ... Data abort: Translation fault, second level
FAR 0x0000000001FD4000
```

拿到 `基址+偏移` 后，在设备上：

```bash
G=workspace/Build/mido/RELEASE_GCC5/AARCH64/.../ArmGicDxe.dll
aarch64-linux-gnu-nm -n --defined-only $G | head -40          # 找符号边界
aarch64-linux-gnu-objdump -d --start-address=0x1600 --stop-address=0x1720 $G
```

本项目靠它把 `X2 = 0xB` 反推成 `MmioWrite32(0x3 + 8, 7)`，直接锁定
`PcdGicInterruptInterfaceBase` 未设。

### 8.3 增量构建陷阱（差点白测一次）

改了**头文件**后 EDK2 未必重编相关模块，`boot-mido.img` 会与上一版**字节相同**。
判据：**每次构建后比较载荷 md5**。

```powershell
# 修正做法：强制刷新时间戳 + 清掉该 SoC 的产出
find Silicon/Qualcomm/msm8953 -name '*.c' -o -name '*.h' | xargs touch
rm -rf workspace/Build/mido/RELEASE_GCC5/AARCH64/Silicon/Qualcomm/msm8953
```

### 8.4 自恢复探针镜像

早期验证封装/跳转时做过一个 `test/probe.img`：载荷只有 0x60 字节
（`b +0x40` + 在 `+0x2C` 写 DTB 偏移 + `smc #0` 调 PSCI `SYSTEM_RESET`）。
它一次证明了四件事：自建 boot.img 被接受、DTB 注入通过校验、lk2nd 会跳任意载荷、
载荷里的 AArch64 代码真的执行了。**而且不需要手动断电**。

### 8.5 一次只改一个变量

显示错位那轮同时改了 bpp 和心跳地址，导致"完全无变化"时无法立刻判断是新引入的问题
还是旧问题——后来不得不回退到已验证版本重做。变量一次一个，成本最低。

## 13. 存储：SDHCI / eMMC / microSD（2026-11 追加）

本节记录 §1–§12 之后新增的工作：把 mido 的两路 SDHCI 控制器驱动起来，以及最终卡在哪里。

### 13.1 已打通的部分

| 项 | 状态 | 关键点 |
|---|---|---|
| SDCC1（eMMC）控制器 | ✅ | HC 模式 + 时钟 + 复位 + `SdMmcPassThru` 全部工作 |
| SDCC2（microSD）控制器 | ✅ | **时钟树是本项目自己开的**（lk2nd 从不碰 SDCC2） |
| eMMC 卡识别 | ✅ | CMD0/1/2/3/7/9/13/16 全部 Success，卡进入 Tran 状态 |
| eMMC 数据读写 | ❌ | CMD17 超时（详见 13.3） |
| microSD 卡识别 | ❌ | 无供电（详见 13.4） |

### 13.2 eMMC 识别的正确序列（重要）

这是本项目最关键的一条「协议语义」结论，来自 lk2nd
`platform/msm_shared/mmc.c:820 mmc_boot_send_relative_address()`：

**对 eMMC，RCA 由主机指定，而不是由卡返回。**

| | SD 卡 | eMMC |
|---|---|---|
| RCA 来源 | 卡自己决定，R6 响应返回 | **主机指定，`MMC_RCA = 2`** |
| CMD3 参数 | `0` | `2 << 16 = 0x00020000` |
| CMD3 响应类型 | R6 | **R1** |
| CMD9/CMD7 参数 | 用卡返回的 RCA | 用 `2` |

可用的序列：

```
CMD0  (Bc)                                   复位
CMD1  (R3, arg 0x40FF8080) 轮询至 bit31=1     OCR = 0xC0FF8080
CMD2  (R2)                                   CID = 0x8BD34B244D42072A...
CMD3  (Ac, R1, arg 0x00020000)               卡接受 RCA=2，进入 standby
CMD9  (Ac, R2, arg 0x00020000)               CSD = 0xEF8E4040FF6DBFF
CMD7  (Ac, R1, arg 0x00020000)               选中，进入 Tran
CMD13 (Ac, R1, arg 0x00020000)               STATUS = 0x00000900（状态=4 Tran）
CMD16 (Ac, R1, arg 512)                      块长
CMD17 (Adtc, R1, arg 0)                      读第 0 块  ← 卡在这里
```

> 早期错误做法：用 R6、传 `0x00010000`、采信卡返回的 `0x40`。结果 CMD3「成功」但卡
> 始终停在 ident 状态，CMD7 永远选不中。这个弯路浪费了很多轮，务必不要重蹈。

### 13.3 卡点：数据传送超时

现象：**所有命令成功，唯一带数据的 CMD17 超时（EFI_TIMEOUT）**。

已排除 / 已验证：

| 假设 | 实验 | 结果 |
|---|---|---|
| 卡未选中 | 先 CMD7 选中再 CMD17 | 选中成功，数据仍超时 |
| 总线位宽不匹配 | 读 `HOST_CTRL1`(0x28) | 本来就是 1 位（bit1=0），不是原因 |
| DMA 选择位不匹配 | `HOST_CTRL1` bits4:3 从 `11` 改成 `10` | 无效（驱动每次传送会重写该寄存器） |
| 缓存一致性 | 注册为 `DmaTypeNonCoherent` | **更糟：所有命令都失败**，已回退 |
| 强制 PIO | 清 `Adma2`+`Sdma` | **更糟：所有命令都失败**，已回退 |
| 改用 SDMA | 只清 `Adma2`（保留 `Sdma`） | 仍超时 |

现象特征：`SdMmcPciHcDxe` 的调试输出伴随 `Error reported by SDHCI / Interrupt status = 8000
/ Error interrupt status = 1`（命令超时）或进程内 TRB 等待超时。

**最可能的方向**（供接手者验证）：
1. ADMA 描述符内存的 cache 维护——EDK2 在 `DmaTypeCoherent` 下完全不做 flush，
   而 msm8953 的 SDCC 不是 cache-coherent。需要确认 `SdMmcPciHcDxe` 是否 Map 了描述符表；
   若没有，需要在分配描述符后手工 `WriteBackDataCacheRange`。
2. 1.8V 时序：`POWER_CONTROL=0x0B`（VDD1=1.8V）、`HOST_CTRL1` bit5=1（1.8V 信号）。
   卡在 HS400 之后 IO 电压是 1.8V，而 1.8V 下 400 kHz 初始化是否稳定值得验证。
3. 干脆不用EDK2 的 SD 栈：照 lk2nd 的 `mmc.c` / `sdhci.c` 自己写一个精简 BlockIo 驱动
   （lk2nd 在这台机器上是验证可用的，最有把握）。

### 13.4 microSD：受限于 RPM 供电

SDCC2 的控制器侧完全正常：RCG 配置、分支使能、软复位、`SdMmcHcInitV4Enhancements`、
400 kHz 时钟供给全部成功（版本 2 = SDHCI 3.0，基频 200 MHz）。但所有命令超时。

原因在 DTB 里：

```
vdd-supply    = <&rpm-regulator>    qcom,vdd-voltage-level = <0x2d0370>   2.95V
vdd-io-supply = <&rpm-regulator>    qcom,vdd-io-voltage-level = <0x1b7740>
```

**SD 槽的 VCC/VCCQ 由 RPM（独立小核上的电源管理器）经 SMD/SPMI 控制**。
lk2nd 从不给 SDCC2 供电（它只从 eMMC 的 boot 分区读内核），所以 UEFI 下这张卡
没有电。要支持 SD，必须先实现 RPM 稳压器客户端（SMEM + APCS IPC 中断 + SMD 协议），
这是一个独立子系统级的工作量。

### 13.5 访问未上电/未开时钟外设的判据

第一次碰 SDCC2 时崩溃：

```
ESR: EC 0x25  ISS 0x10   Data abort: Synchronous external abort
FAR = 0x078649FE         (SDCC2_SDHCI_BASE + VERSION)
```

**`Synchronous external abort` + 合理地址 = 该外设时钟门控关闭**（不是地址没映射；
地址没映射会报 `Translation fault`）。这是排查任何新外设时的第一条判据。

### 13.6 SDCC2 时钟树完整序列（已验证可用）

```c
MmioWrite32(0x01843000, 0);                    // BCR：解除块复位
MmioWrite32(0x0184300C, 0);                    // M
MmioWrite32(0x01843010, 0);                    // N
MmioWrite32(0x01843014, 0xFFFFFFFF);           // D
cfg = MmioRead32(0x01843008);                  // CFG_RCGR
cfg &= ~((0x7<<8) | 0x1F | (0x3<<12));
cfg |= (1<<8) | 0x1F;                          // src=GPLL0(800MHz), div=16 → 50MHz
MmioWrite32(0x01843008, cfg);
MmioOr32(0x01843004, 1);                       // CMD_RCGR：触发更新
while (MmioRead32(0x01843004) & 1) ;           // 等待完成
MmioOr32(0x0184301C, 1);  // AHB_CBCR 使能，等 bit31=0
MmioOr32(0x01843018, 1);  // APPS_CBCR 使能，等 bit31=0
```

实测：`CFG_RCGR` 读回 `0x11F`，时钟稳定位立刻置起（`CLOCK_CONTROL = 0x3`），
基频 200 MHz 上报正常。这套「BCR → RCG → CMP 更新 → CBCR 使能」的流程对
msm8953 上任何外设时钟都通用。

### 13.7 另一条经验：不要绕过 EmmCxe 就以为万事大吉

`SdMmcPciHcDxe` 只提供 `SdMmcPassThru`（命令通道），**设备路径分类、总线宽度、
分区枚举都在 `EmmcDxe` 里**。本项目为了诊断绕过了 `EmmcDxe` 直接发命令，
结果踩到两个坑：
- `EmmcDxe` 拒绑原因之一是 `BuildDevicePath()` 生成 SD 节点（`SlotType` 来自
  CAPABILITIES bits30:31，本机读作 0 = Removable），需要把 eMMC 槽位标成 `EmbeddedSlot`；
- `MediaPresent` 依赖 SDHCI `PRESENT_STATE` bit16（Card Inserted），eMMC 焊死无卡检测
  引脚，该位恒 0，必须绕过检查。

这两点都已写成补丁（见 `scripts/build-mido-all.sh` 的 2 与 2b 段）。
